# Exact-fork LLVM source-built Maven native proof

The six-language Ubuntu LLVM 18 test in the Maven CI is **distribution-binary evidence**, not proof of the selected LLVM fork. This separate and intentionally slower workflow checks out `hsoliwal/llvm-project` at the exact audited commit `591f3d1edf0a9ee718d17a0ee70dd013b3c01908` (LLVM major 24), verifies that its checkout has no modified or untracked source, then builds the *original* LLVM Clang, Clang++ and `llc` from those sources with CMake/Ninja. The source is sparse-checked out with the required `llvm`, `clang`, `cmake`, `third-party`, and `libc` sibling directories. The build and its evidence live outside that source tree.

Before the expensive source build, the workflow also runs an original-script negative admission gate. It verifies Bash syntax, exit 64 on missing arguments, exit 65 on overlapping source/build or build/evidence destinations, and exit 66 on a wrong Git revision. Every refusal must leave the test source tree and proposed build/evidence directories unchanged. The source-built proof runner itself creates no output directories until the exact checkout hash, clean worktree, required source closure, and LLVM major-version checks all pass. It additionally requires **fresh outputs**: each build/evidence destination must be absent or an empty directory. Non-empty directories (including hidden state, an old `CMakeCache.txt`, stale binaries or a previous `source-receipt.tsv`) and regular-file destinations fail with exit **65**, before any build or evidence write. Pre-created empty directories remain valid. This prevents a stale CMake/Ninja configuration or earlier success record from being mistaken for execution from the current pinned source. The CI admission test uses the real, pinned checkout for the occupied-output cases; local stub-based refusal tests do not establish source/binary provenance. This admission check executes no LLVM compiler.

The workflow uses the original LLVM build targets and host X86 target back end; no Java compiler, LLVM assembler, native linker, IR optimizer, source parser, or scheduling framework is reimplemented. It invokes Maven's **existing** `LlvmCompilerIntegrationTestMain --required` against the newly compiled `build/bin` tools. The test exercises real C17, C++20, Objective-C, both Objective-C++ aliases, and an LLVM IR object generated by the source-built `llc` and linked with Clang. It requires the test to demonstrate native header mutation/invalidation, failure/recovery and rejection of unqualified native cache skips. The JDK 21 toolchain is a separate host input; the original JNI/ABI and Java release gates retain their owners.

The pinned source receipt contains the source repository and **verified exact commit**, hashes of key CMake and Clang-driver source files, original compiled executable SHA-256 values, CMake configuration, actual native build output, Maven `test-compile`, and the original Java task-runner output. No binary payload is published as a release or silently promoted to Gradle. The capture uses `pipefail`, strict tool availability checks, explicit file and path ownership and a fail-closed required-log signature. An incomplete check cannot issue the final success record.

The proof is deliberately narrower than the six-language distribution test. **Flang is NOT source-built in this lane.** Its runtime, target SDK and Fortran linking require independent configuration and qualification. `mlir-opt`, `mlir-translate`, LLD, Wasm/COFF, CTest, JNI/ORC, Windows/macOS, alternate target triples and full toolchain/system-library provenance also remain separate gates. The host compiler, sysroot, CMake/Ninja versions, and operating-system libraries are environmental inputs, and the source-built result is qualified only on the observed runner. This gate does not authorize LLVM provider reuse or artifact cache restoration.

To replay with an exact checked-out fork and supported host toolchain:

```sh
bash tools/m3-polyglot-maven-plugin/scripts/verify-pinned-llvm-fork.sh \
  /work/llvm-fork-checkout \
  /work/llvm-fork-build \
  /work/llvm-maven-evidence
```

Do not enable automatic fetching, source mutations, native toolchain substitutions, or user-controlled arguments that would silently override the source pin. Preserve upstream LLVM Apache-2.0 WITH LLVM-exception provenance and the existing Maven/Java/Synexia licensing. This is a separate real source-build PR check; it must be **executed** before claiming fork-native qualification. A GitHub job that is queued, cancelled, or skipped is not proof.

## Change-sensitive source-build coverage

A successful exact-fork build qualifies a **specific Maven runner and
compiler-adapter implementation**. Changing the Java owner, the native test, or
the Maven packaging can invalidate that result even when the LLVM source pin
and this script are unchanged. Therefore the `master` push and pull-request
path filters for `.github/workflows/m3-llvm-fork-source-proof.yml` must be
**identical** and must cover the implementation and test owners used by this
gate: `LlvmCompilerProvider`, `TaskManifest`, `TaskRunner`,
`InputStamps`, `BuildCache`, `M3ToolProvider`,
`M3ToolProviders`, `M3ToolReuseInputs`, the native LLVM integration
regression, the provider service registry file and the plugin `pom.xml`,
in addition to the source-proof script, workflow, and this guide.

The offline verifier at
`scripts/verify-llvm-fork-source-triggers.py` checks that both trigger
lists contain the same, nonduplicated mandatory paths before the potentially
expensive original LLVM fetch/compile. It reads only the workflow and
repository; no native tool is invoked and no source file is modified.
Its own path is included in the trigger contract to prevent verification
drift. A failure blocks that CI run, not the original Maven build or normal
IDE/Gradle consumers.

This is a source-provenance *invalidation trigger*, not a native-cache
admission rule. The LLVM compiler and optional LLVM tools providers continue executing normally
unless independently qualified; an executable SHA-256 alone cannot authorize
artifact restoration. The opt-in compilation-database exporter has a separate
CI owner because it does not participate in the exact-fork TaskRunner test.
